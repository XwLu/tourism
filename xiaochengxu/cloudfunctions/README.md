# 评论与报名的云开发配置

`travel-social` 为小程序提供共享评论、整趟旅行报名和头像昵称存储。行程浏览保持本地加载，网页没有接入这套互动功能。

## 首次启用

1. 在当前 AppID 对应的微信开发者工具中打开「云开发」，创建或选择一个环境。将环境 ID 填入 `config/cloud.js` 的 `cloudEnvironmentId`；这不是 AppID。收费情况以云开发控制台当前套餐为准。
2. 在该环境的数据库中创建 `travel_profiles`、`travel_members`、`travel_comments` 三个集合。三个集合均设置为禁止客户端直接读写：

   ```json
   { "read": false, "write": false }
   ```

   数据统一通过云函数读取和写入。云函数使用服务端微信身份，不接受客户端提供的用户 ID。
3. 云存储使用「所有用户可读，仅创建者可写」权限，让同行者可以看到头像。头像保存在 `travel-avatars/` 下，不要将这些图片设为仅自己可读。
4. 在开发者工具中选中相同环境，右键 `cloudfunctions/travel-social`，选择「上传并部署：云端安装依赖」。项目已设置 `cloudfunctionRoot`，云函数源码不随小程序客户端包发布。函数的 `config.json` 声明了 `security.msgSecCheck` 权限，用于检查昵称和评论；部署时同步上传配置。
5. 在数据库控制台添加下列索引，字段顺序与方向保持一致：

   | 集合 | 索引字段 |
   | --- | --- |
   | `travel_members` | `tripId` 升序、`joinedAt` 降序、`_id` 降序 |
   | `travel_members` | `userId` 升序 |
   | `travel_comments` | `tripId` 升序、`dayId` 升序、`createdAt` 降序、`_id` 降序 |

6. 在小程序管理后台完善用户隐私保护指引，按实际使用情况声明头像、昵称及相关用途。重新编译，使用两个体验成员微信账号验证报名和评论共享，再上传体验版。

未填写环境 ID 时，行程可以正常浏览，评论和报名显示暂未开放。连接失败时会提示重试，不会把本机存储伪装成共享数据。

## 交互规则

- 报名按整趟旅行记录：同一微信用户在同一旅行只产生一份报名记录，各日期显示同一组同行成员。页面仅展示最近报名的三位成员头像及总人数。
- 评论按旅行 ID 和日期 ID 分开保存，每条最多 500 字，按发布时间倒序展示，每页 20 条；可以删除自己的评论。
- 首次报名或发评论时，通过微信 `chooseAvatar` 按钮和 `nickname` 输入框选择头像、填写昵称。只有点击确认后才保存。服务端用 `getWXContext().OPENID` 区分微信身份，存储其哈希标识；不会获取微信号、手机号或好友列表，也不向其他用户返回身份标识。
- 昵称和评论经微信文字内容检查通过后才保存。头像和昵称保存在个人资料中，后续报名及评论复用；修改资料会同步更新报名头像昵称，历史评论保留发布时的资料。
- 重复点击报名不会增加人数；评论提交使用请求 ID，网络失败后重试同一条反馈不会产生两份记录。提交失败时保留输入，切换日期分别保留本次打开页面期间的草稿。
- 云开发环境 ID、客户端代码和云函数必须部署到同一个小程序对应的环境。无需在客户端写入 AppSecret。

## 修改行程

云函数的 `travel-social/trips.json` 是允许互动的旅行和日期列表。新增旅行或修改日期时，与 `data/trips.js` 和对应行程数据同步更新，并重新部署云函数。所有数据集合使用 `tripId` 和 `dayId` 关联，不依赖客户端页面标题。

## 验证建议

1. 账号 A 在任一日期报名；其他日期也显示「已报名」，刷新或重新进入后仍保留。
2. 账号 B 报名；A 重新打开页面可以看到 B 的头像和人数变化。重复报名不会重复计数。
3. A 在 10 月 1 日评论，切到 10 月 2 日不会显示该评论；B 在 10 月 1 日可以看到 A 的反馈。
4. B 只能删除自己的留言，不能删除 A 的留言。评论多于 20 条时可继续加载，时间相同的留言也不应丢失。
5. 断网时保留输入并提示失败；快速切换日期时，较早的请求结果不会覆盖当前日期。
6. 头像选择、微信昵称填充、云端内容检查及隐私声明匹配需要在真实微信环境中验证。
